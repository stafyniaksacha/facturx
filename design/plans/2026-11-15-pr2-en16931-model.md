# PR ② — EN 16931 model and CII mapping Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A public, typed model keyed by EN 16931 business terms (plus `EXT-FR-FE-*`), with `fromCii()` / `toCii()` mapping it losslessly to and from the existing CII classes, proven on every corpus document.

**Architecture:** Classes in `src/lib/models/en16931/`, one per business group. A mapping layer in `src/lib/mapping/cii/` converts between that model and `CrossIndustryInvoiceType`; the existing `invoiceToXml` / `xmlToInvoice` stay the only CII XML code. `fromCii` computes `dropped` **by difference**: it maps CII → model, maps the model back with `toCii` at the document's level, and reports every CII path whose value didn't survive. So `dropped` is complete by construction, whatever the mapping misses.

**Tech Stack:** TypeScript (ESM), vitest on the built `dist/`.

**Spec:** [`design/2026-11-15-ubl-en16931-model-design.md`](../2026-11-15-ubl-en16931-model-design.md), section "PR ② — the EN 16931 model and its CII mapping". **Stacked on PR ①** (branch from its tip).

## Global Constraints

- Everything in PR ①'s Global Constraints applies.
- `Models` (CII) and every existing export are unchanged; the new API is additive.
- Scope of the model: every EN 16931 BT/BG, plus every `EXT-FR-FE-*` id in `spec/afnor-xp-z12-012-1.4/text/annex-a--Flux_2_UBL_EXT-CTC-FR.csv` and `annex-a--CII_D22B_FX_EXT-CTC-FR.csv`. Not Factur-X fields that have neither kind of id ("true BT-X").
- CII placement follows the Factur-X field matrices (`spec/factur-x-1.09/text/fields--Factur-X_CII_D22B_<PROFILE>.csv`, `Xpath` column 17) at every level, as `src/lib/converters/facturx.ts` already does. Never follow annex A where CG-39 says it is shifted.
- Cardinality: the wider of the EN 16931 column (`EN16931 Semantic Cardinal`, matrix column 8) and EXTENDED-CTC-FR (annex A `Card UBL XML EXTENDED`). `n` → array; `1..` → required property.
- Values: amounts / quantities / prices / percentages `number`; dates ISO `YYYY-MM-DD` `string`; identifiers with a scheme `Identifier { value: string, schemeId?: string }`; codes `string` with the code list named in JSDoc.
- Every property and class carries its id in JSDoc: `@bt BT-n`, `@bg BG-n`, `@ext EXT-FR-FE-n` / `@ext EXT-FR-FE-BG-n`.
- Naming: classes are the EN 16931 group name in PascalCase (`Seller`, `VatBreakdown`, `InvoiceLine`); properties the business-term name in camelCase without the group prefix (`BT-27 Seller name` on `Seller` → `name`). `EXT-FR-FE` fields take the English name the EXTENDED matrix gives the same XPath; translate the French term only when there is none.
- `fromCii` levels: `basic`, `en16931`, `extended`, `extended-ctc-fr`. `minimum` / `basicwl` throw `Error('… is not an EN 16931 invoice …')`.
- `toCii` throws, naming the business term, on an `EXT-FR-FE` value with `level` `basic` / `en16931`.

## Review Focus

1. **A Factur-X EXTENDED document with true BT-X content** (e.g. corpus EXTENDED PDFs with `ram:ProductCharacteristic` beyond BG-32, logistics service charges): `dropped` lists those paths, nothing else is lost. → Task 6 corpus test.
2. **A date not in format `102`** in an EXTENDED document: not representable as ISO date → appears in `dropped`, never mangled. → Task 2 test `reports a non-102 date as dropped`.
3. **Sub-cent unit prices and many-digit quantities** (annex B UC11 / UC13) survive the trip exactly. → Task 4 test.
4. **Non-ASCII and XML-special text** (`&`, `<`, `é`, `€`) in names and notes survives `fromCii → toCii → invoiceToXml → xmlToInvoice`. → Task 6 stress test.
5. **Calling `toCii` without `level`** on an invoice that holds `EXT-FR-FE` values: required option → TypeScript error; at runtime a clear throw. → Task 1 test.

**Interfaces (produced, used by every later task and by PR ③):**

```text
// src/lib/models/en16931/
export class Identifier { value: string; schemeId?: string }
export class Invoice { /* BG-0: header terms of this task + the groups of Tasks 2-5 */ }
export type En16931Level = 'basic' | 'en16931' | 'extended' | 'extended-ctc-fr'

// src/lib/mapping/cii/index.ts
export function fromCii(cii: CrossIndustryInvoiceType): { invoice: Invoice, dropped: string[] }
export function toCii(invoice: Invoice, options: { level: En16931Level }): CrossIndustryInvoiceType
```

Header terms in this task: BT-1, BT-2, BT-3, BT-5, BT-6, BT-7, BT-8, BT-9, BT-10, BT-11, BT-12, BT-13, BT-14, BT-15, BT-16, BT-17, BT-18 (+ scheme BT-18-1), BT-19, BT-23, BT-24, BG-1 (notes, BT-21/22), BG-3 (preceding invoices, BT-25/26), BG-14 (BT-73/74, BT-8 period), BG-24 (BT-122…125-2, attachments as `{ content: string (base64), mimeCode, filename }`). Their header-level `EXT-FR-FE` fields go here too.

`dropped` algorithm (`dropped.ts`): `diffPaths(a: CrossIndustryInvoiceType, b: CrossIndustryInvoiceType): string[]` walks both models and returns XPath-like paths (`/rsm:…/ram:…[n]`) of every leaf value present in `a` and absent or different in `b`. `fromCii` = map, then `dropped = diffPaths(cii, toCii(invoice, { level }))`, with `level` read from BT-24 via `levelFromGuidelineId`.
